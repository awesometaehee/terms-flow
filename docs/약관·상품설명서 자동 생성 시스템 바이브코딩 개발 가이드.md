# 약관·상품설명서 자동 생성 시스템 바이브코딩 개발 가이드

> 기준: 약관 상품 생성 시스템 회의 녹취와 후속 결정사항, 첨부 상품 구성 표 이미지.  
> 상태: 개발 초안. 이 문서의 **확정**은 회의 또는 사용자의 후속 답변으로 정해진 업무 규칙을 뜻하며, **권장안**은 구현을 위한 제안이다.  
> 작성일: 2026-10-22 · 방향 전환 반영: 2026-10-23

## 0. 방향 전환: KMS (2026-10-23 확정)

시스템의 중심을 **약관·상품설명서 구분 없는 KMS(지식 관리 시스템)**로 바꾼다. 1장 이후의 상품별 3종 문서 자동 생성은 KMS 안의 한 기능("상품 문서")으로 유지한다.

| 항목 | 확정 내용 |
|---|---|
| 기본 단위 | **모듈**(재사용 단락, 지식 라이브러리)과 **문서**(모듈·직접 쓴 단락의 조합). 문서 종류 구분 없음 |
| 문서 만들기 | 새 문서(빈 문서 또는 다른 문서 복제) → 모듈을 하나씩 골라 넣기 → **끌어서 순서 변경** → 단락 사이 **+**로 모듈·빈 단락 삽입 |
| 편집 | 단락마다 서식 편집기. 글자를 선택하면 도구 막대: 단락 형식(본문·제목 1~3), 굵게·기울임·밑줄·취소선, 글자 색, 형광펜, 정렬 4종, 글머리·번호 목록, 들여쓰기·내어쓰기, 링크, 변수 넣기 |
| 문서 안 수정 | 기본은 **이 문서에만 반영**(원본 모듈 유지, "문서에서 수정됨" 표시). 필요하면 **원본 모듈에 반영**해 새 모듈 버전으로 저장 |
| 변수 | `[서비스명]`, `[14]` 같은 **값이 채워지는 변수 칩**. 변수는 이름·형식·기본값을 정의하고, 값은 문서마다 입력. 값이 없고 기본값도 없으면 발행 불가 |
| 분류·검색 | 모듈·문서 공용 **카테고리 트리**와 **태그**, 제목·본문 **전체 검색**(PostgreSQL pg_trgm 부분 일치) |
| 출력 | 문서를 버전별 **PDF·PNG**로 발행 (기존 렌더링 파이프라인) |
| 일괄 반영 | 모듈 새 버전 → **사용 중** 문서 중 그 모듈을 **수정 없이** 쓰는 문서만 새 리비전·발행본 생성. 작성 중·종료 문서, 문서에서 고친 단락은 제외(사유 표시) |
| 문서 상태 | 작성 중 → 사용 중 → 종료. 종료 문서는 읽기 전용(DB 트리거로도 보호) |
| 승인 워크플로 | 이번 범위에서 제외 |

구현 상세는 `docs/구현 계획.md` 11절.

## 1. 목표와 범위

상품을 등록할 때 **약관, 약관 주요 내용, 상품설명서**의 3종 문서를 한 세트로 생성한다. 공통 문구를 한 번 수정하여 **현재 판매 중인 상품**의 새 문서 버전에 반영하는 것이 최우선 목표다. 상품별 품목과 서비스는 유동적이므로 가변적인 데이터로 입력하고, PDF와 페이지별 PNG를 출력한다.

### 확정된 업무 규칙

| 항목 | 규칙 |
|---|---|
| 문서 세트 | 상품마다 약관, 약관 주요 내용, 상품설명서 3종을 생성한다. 개별 파일과 통합본을 다룰 수 있어야 한다. |
| 약관 | 공통 조항을 기본으로 하고 판매 채널의 협력비 조항, 환급 방식·비율 문구, 결합 상품 조항 등을 조합한다. 조항 순서를 제어한다. |
| 약관 주요 내용 | 대체로 공통 양식이며 상품명, 법인 정보 등 일부 값이 달라진다. |
| 상품설명서 | 일반형과 결합 상품형 양식이 있다. 상품 가격대·구성에 따라 품목이 달라지며, 한 상품명 아래 여러 금액대가 한 문서에 들어갈 수 있다. |
| 일괄 수정 | 공통 내용의 수정은 **활성 판매 상품에만** 적용한다. **과거 판매 상품에는 적용하지 않는다.** |
| 문서 이력 | 문서를 버전별로 조회할 수 있어야 한다. 발행된 과거 버전은 재현 가능해야 한다. |
| 상품 구성 | 품목·서비스 항목의 수와 계층이 유동적이다. JSON 형식 등록 제안을 반영한다. |
| 출력 | PDF와 PNG가 필요하다. PDF는 보관·전달, PNG는 전자청약 게시 등에 사용된다. |
| DB·실행 환경 | DB는 **PostgreSQL**을 사용한다. **개발은 Docker 없이 로컬**(PC에 설치한 PostgreSQL, `uv`·`pnpm`으로 실행)에서 하고, **운영은 Docker**(Docker Compose: PostgreSQL·저장소·API·worker·화면)로 배포한다. |
| 기술 스택 | 아래 "기술 스택" 절의 제안안을 채택해 진행한다. |

### 기술 스택

회의에서 정해지지 않았던 기술 스택은 이 가이드의 제안안으로 진행하기로 했고, 이후 백엔드 언어를 Python으로 정했다. 선정 기준은 세 가지다. 백엔드(API·작업 처리·렌더러)는 Python 하나로 통일하고, PostgreSQL 외 인프라는 최소화하며, PDF와 PNG가 같은 렌더링 결과에서 나와야 한다.

| 영역 | 선택 | 선택 이유 |
|---|---|---|
| 백엔드 언어·런타임 | Python 3.13, 패키지 관리 uv (`uv.lock`) | API·작업 처리·렌더러가 한 코드베이스에서 도메인 모델을 공유한다. |
| 저장소 구성 | `backend/`(API·워커 공용 Python 패키지), `frontend/`(React), `schemas/`(품목 구성 JSON Schema) | 품목 JSON Schema는 `schemas/` 한 곳에서 관리하고 백엔드·프론트엔드가 같은 파일을 사용한다. |
| 백엔드 API | FastAPI | 타입 힌트 기반 요청 검증과 OpenAPI 문서가 자동 생성된다. 도메인은 상품·조항·템플릿·문서 세트·일괄 수정 모듈로 나눈다. |
| DB·마이그레이션 | PostgreSQL 17 + SQLAlchemy 2.x + Alembic, 드라이버 psycopg 3 | JSONB 지원, 리비전 기반 마이그레이션. 유일 인덱스·트리거 등 제약도 Alembic 마이그레이션으로 관리한다. |
| 입력 검증 | Pydantic v2(API 요청) + `jsonschema`(품목 구성 JSON Schema 2020-12) | 품목 구성은 `schemaVersion`별 JSON Schema 파일로 버전 관리하고, 필드 경로가 있는 오류를 반환한다. |
| 비동기 작업 | Procrastinate (PostgreSQL 기반 작업 큐) | Redis 없이 발행·일괄 수정 작업을 큐로 처리한다. 재시도와 작업 ID 기반 중복 방지에 사용한다. |
| 템플릿 엔진 | Jinja2 (`autoescape` 활성화) | 자동 HTML 이스케이프가 적용된다. 조항 선택과 순서는 템플릿이 아니라 서버의 조합기가 결정하고, 템플릿에는 로직을 최소화한다. |
| PDF 렌더링 | Playwright for Python(Chromium) HTML → PDF, `pypdf`로 통합본 병합 | HTML/CSS 인쇄 레이아웃(`@page`, 페이지 나눔)을 그대로 사용한다. |
| PNG 변환 | PDFium(`pypdfium2`)으로 PDF 페이지별 래스터화 | 화면을 따로 캡처하지 않고 생성된 PDF에서 바로 변환해 PDF와 PNG의 내용 일치를 보장한다. pip로 설치되어 Windows 로컬 개발에도 별도 프로그램이 필요 없다. |
| 한글 글꼴 | 운영: Noto Sans CJK KR / Noto Serif CJK KR (OFL, Debian `fonts-noto-cjk`)을 worker 이미지에 포함. 로컬 개발(Windows): 맑은 고딕으로 대체 | 시스템 글꼴에 의존하지 않아 어느 환경에서 렌더링해도 결과가 같다. 회사 지정 글꼴이 있으면 라이선스 확인 후 교체한다. |
| 파일 저장소 | 운영: S3 호환 스토리지(`boto3`), compose의 SeaweedFS 컨테이너(MinIO 공식 이미지 배포 중단으로 대체). 개발: 로컬 폴더(`STORAGE_BACKEND=local`, `data/storage`) | DB에는 저장 키와 SHA-256만 둔다. 운영 저장소는 추후 결정하되 S3 API로 통일한다. |
| 프론트엔드 | TypeScript, React + Vite, TanStack Query, Mantine, pnpm | 표 형태 품목 편집, 탭, 폼 검증 UI를 빠르게 구성한다. API 타입은 FastAPI의 OpenAPI 스키마에서 `openapi-typescript`로 생성한다. |
| 테스트 | pytest + httpx(API 통합, 로컬 PostgreSQL의 별도 테스트 DB), Vitest(프론트 단위), Playwright(E2E·화면) | 수용 테스트 A1~A12를 자동화한다. |
| 품질 도구 | 백엔드: Ruff(린트·포맷), mypy `strict` / 프론트: ESLint, Prettier, TypeScript `strict` | 일관된 코드 스타일과 타입 안정성. |

**원칙:** 라이브러리 버전은 `uv.lock`, `pnpm-lock.yaml`과 Docker 이미지 태그로 고정한다. 렌더러 버전(Chromium·PDFium 버전, PNG 해상도, 실행 OS)은 문서 세트 manifest의 `renderer_version`에 기록해 과거 버전의 재현 근거로 삼는다. 스택을 바꿀 때는 이 표를 먼저 수정한다.

### 이번 범위에서 분리할 사항

- **추후 고려:** 템플릿 관리 권한과 세부 역할별 접근 제어.
- **추후 고려:** OKMS/KMS, 전자청약, 회사 웹사이트, 외부 출력 업체 등의 자동 연동. 초기 버전은 파일 생성과 다운로드까지 구현한다.
- **미확정:** PDF·인디자인 업로드 후 화면에서 원본의 특정 텍스트를 직접 선택·편집하는 기능. 회의에서는 초기 화면 구상으로 제시되었으나 최종 구현 방식으로 확정되지 않았다. 1차 개발에서는 구조화된 템플릿·입력값 편집을 권장한다.
- **미확정:** 법인명, 대표자, 시험 일자, 선수금 관련 문구 등 각 데이터의 최종 승인 담당자와 적용 범위. 데이터 항목은 마련하되 실제 일괄 적용 규칙은 업무 담당자 검토 후 확정한다.

## 2. 용어와 핵심 모델

- **상품 계열(product):** 같은 상품명과 문서 구조를 공유하는 단위.
- **판매 구성(variant):** 동일 상품 안의 금액대·호수·품목 구성별 선택지. 단일 구성 상품도 배열 1개로 표현한다.
- **상품 버전(product_revision):** 상품 데이터가 변경될 때마다 저장하는 불변 스냅샷.
- **템플릿 버전(template_revision):** 문서 종류별 레이아웃과 조항 배치의 불변 버전.
- **조항 버전(clause_revision):** 공통 문구나 조건부 조항의 불변 버전.
- **문서 세트 버전(document_set_version):** 특정 상품 버전, 템플릿 버전, 조항 버전 및 렌더링 결과를 고정한 발행 단위.

**권장안:** 상품 상태는 `DRAFT`, `ACTIVE`, `ENDED`로 구분한다. 일괄 적용 대상은 실행 시점에 `ACTIVE`인 상품으로 고정한다. `ENDED`는 과거 판매 상품으로 취급하며 문서 재생성·내용 변경을 허용하지 않는다. 단, 과거 버전 조회와 기존 파일 다운로드는 허용한다. 과거 데이터 오류를 바로잡아야 한다면 별도 승인 절차를 정의할 때까지 일반 편집·일괄 수정 흐름 밖에서 처리한다.

## 3. 사용자 흐름

1. 사용자가 상품명, 법인, 판매 채널, 환급 방식, 결합 상품 여부와 하나 이상의 판매 구성을 등록한다.
2. 시스템은 해당 조건에 맞는 약관 조항과 상품설명서 양식을 제안한다. 사용자는 적용 조항과 순서를 확인한다.
3. 미리보기에서 3종 문서와 통합본을 확인하고 발행한다.
4. 발행 시 상품·템플릿·조항·입력값 스냅샷과 PDF/PNG 결과를 새 문서 세트 버전으로 보관한다.
5. 공통 문구 수정 시 영향받는 **현재 활성 판매 상품** 목록을 먼저 보여준다. 사용자가 실행하면 대상별 새 문서 세트 버전을 생성한다. 기존 버전과 종료 상품 문서는 그대로 둔다.
6. 상품 상세에서 문서 세트 버전 목록을 열고, 각 버전의 생성 시각·변경 사유·적용 조항·PDF/PNG를 조회한다.

## 4. 상품 구성 데이터: JSONB 권장안

첨부 표에는 `고인 용품`, `꽃장식`, `장례 행사`, `일회성 용품`, `서비스 제공품` 등 묶음 아래 다양한 행이 있다. 관, 수의, 도포·한복, 차량, 장례지도사, 의전관리사 등은 세부 항목·규격·제공 조건이 서로 다르다. 따라서 모든 품목을 단일 테이블의 고정 열로 만들기보다 **판매 구성별 `composition_jsonb`**에 순서 있는 그룹과 항목을 저장한다. 아래 명칭과 값은 이미지 구조를 설명하기 위한 **예시**이며 실제 상품의 확정 조건이 아니다.

```json
    },
    {
      "id": "staff_service",
      "label": "인력 서비스",
      "order": 30,
      "items": [
        {
          "id": "ceremony_manager",
          "label": "행사의전사",
          "specification": null,
          "quantity": { "value": 1, "unit": "명" },
          "notes": [],
          "order": 10
        }
      ]
    }
  ],
  "footnotes": ["추가 비용과 제공 조건은 승인된 문구를 사용"]
}
```

같은 상품에 여러 금액대가 있으면 `product_variants`에 `variant_code`, `display_name`, `price_amount`, `composition_jsonb`를 각각 저장한다. 렌더러는 판매 구성 1개면 단일 열, 2개 이상이면 금액대별 비교 열을 만든다. **권장안:** 복잡한 품목의 하위 행이 필요할 때 `children` 배열을 허용하되, 첫 버전에서는 깊이를 2단계로 제한한다.

**검증 규칙 권장안:** `schemaVersion` 필수, 그룹·항목 ID는 해당 구성 안에서 유일, `order`는 정수, `label`은 공백이 아니어야 한다. `quantity`는 `null` 또는 양수와 단위로 제한한다. 알 수 없는 필드는 저장 전에 거부해 오타를 잡는다. 허용할 그룹 종류와 필수 품목은 상품 종류별 검증 프로필로 관리한다. 저장 시 JSON Schema 검증을 수행하고, 발행 시 참조 이미지·추가 비용 문구 등 필수 확인 항목을 다시 검사한다. 자주 검색하는 상품명·가격·상태·채널은 JSONB에만 넣지 말고 일반 열로 둔다.

## 5. 템플릿과 조항 조합

### 구성 규칙

| 문서 | 조합 방식 |
|---|---|
| 약관 | 필수 공통 조항 + 조건부 조항(협력비, 환급, 결합 상품) + 상품별 값. 조항은 안정적인 `clause_key`와 표시 순서를 갖는다. |
| 약관 주요 내용 | 공통 템플릿 + 상품명·법인 정보 등의 변수. |
| 상품설명서 | 일반형 또는 결합 상품형 + 판매 구성별 품목 표 + 승인된 공통 안내 문구. |

**권장안:** 조건은 사용자 입력값으로 결정한다. 예를 들어 오프라인 판매면 협력비 조항을 포함하고, 온라인 판매면 제외한다. 환급 방식은 승인된 문구 중 해당 값을 선택한다. 결합 상품이면 관련 조항과 설명서 블록을 추가한다. 실제 조항 번호와 문구는 법무·업무 담당자가 승인한 원본을 입력해야 하며 개발자가 임의로 생성하지 않는다. 조항 순서는 템플릿의 `order`를 기본으로 하되 발행 전 화면에서 확인하도록 한다.

공통 문구는 참조 키로 관리한다. 예: `company.legal_name`, `company.representative`, `disclosure.pt_test_date`, `disclosure.reserve_statement`. 공통 문구를 편집할 때는 새 조항 버전을 만들고, 영향을 받는 활성 상품을 대상으로 새 문서 버전을 생성한다. 발행 문서를 렌더링할 때는 “현재 최신 조항”을 동적으로 읽지 않는다. 각 발행 버전이 사용한 조항 버전을 고정해야 과거 출력과 재조회 결과가 같아진다.

## 6. DB 설계 권장안

**확정 기술:** DB는 PostgreSQL이다. 개발은 PC에 설치한 PostgreSQL과 로컬 실행, 운영은 Docker Compose로 한다. 품목 구성 등 가변 데이터는 PostgreSQL의 `JSONB`에 저장한다. 아래는 논리 모델이다.

### 6.1 개발·운영 환경 구성

**개발 (로컬, Docker 미사용)**

- **DB:** PC에 설치한 PostgreSQL(17 이상)을 쓴다. 앱 전용 사용자와 DB를 만들고, 테스트 DB(`{DB명}_test`)를 자동으로 만들 수 있도록 앱 사용자에게 `CREATEDB` 권한을 준다.
- **실행:** 백엔드는 `uv`(Python 3.13 가상환경), 화면은 `pnpm`으로 실행한다. API(`uvicorn`), worker(`python -m procrastinate ... worker`), 화면(`pnpm dev`)을 각각 띄운다.
- **파일 저장소:** 저장소 루트의 `data/storage` 폴더(`STORAGE_BACKEND=local`). 테스트는 `data/storage-test`.
- **렌더러:** `uv run playwright install chromium`으로 Chromium을 받는다. Windows 한글 글꼴은 맑은 고딕을 쓴다.
- 접속 정보는 저장소 루트의 `.env`(템플릿 `.env.example`)로 주입하고 커밋하지 않는다.

```sql
-- 로컬 PostgreSQL에서 1회 실행 (관리자 계정). 비밀번호는 .env와 같게 직접 정한다.
CREATE ROLE terms_flow LOGIN CREATEDB PASSWORD '<비밀번호>';
CREATE DATABASE terms_flow OWNER terms_flow;
```

**운영 (Docker Compose)**

- `docker compose --env-file .env.production up -d --build`로 `db`(postgres:17), `storage`(SeaweedFS), `migrate`(Alembic), `api`, `worker`(Chromium·Noto CJK 포함), `web`(nginx: 빌드된 화면 + `/api` 프록시)을 기동한다.
- DB·저장소·API는 외부 포트를 열지 않고, 화면 포트(`WEB_PORT`)만 연다. 데이터는 이름 있는 볼륨(`pgdata`, `storagedata`)에 둔다.
- 이미지 태그는 메이저 버전 이상을 고정하고 `latest`는 쓰지 않는다. 비밀번호·키는 `.env.production`(템플릿 `.env.production.example`)에만 둔다.
- 스키마는 Alembic으로 관리하며, 배포 시 `migrate` 서비스가 `alembic upgrade head`를 실행한다.

### 6.2 테이블 논리 모델

| 테이블 | 핵심 열 | 목적·제약 |
|---|---|---|
| `products` | `id`, `name`, `company_id`, `status`, `channel`, `refund_type`, `bundle_type`, `created_at` | 상품 계열. 상태 변경 이력을 별도 기록. |
| `product_variants` | `id`, `product_id`, `variant_code`, `display_name`, `price_amount`, `composition_jsonb`, `sort_order` | 금액대별 구성. `product_id + variant_code` 유일. |
| `product_revisions` | `id`, `product_id`, `revision_no`, `snapshot_jsonb`, `created_at`, `change_reason` | 발행에 쓰인 상품 전체 입력 스냅샷. 수정 금지. |
| `templates` | `id`, `document_type`, `template_key`, `status` | 문서 종류별 템플릿 식별자. |
| `template_revisions` | `id`, `template_id`, `revision_no`, `layout_definition`, `created_at` | 레이아웃·블록 순서 스냅샷. |
| `clauses` | `id`, `clause_key`, `document_type`, `kind` | 공통·조건부 조항의 안정적인 식별자. |
| `clause_revisions` | `id`, `clause_id`, `revision_no`, `content`, `created_at`, `change_reason` | 승인된 조항 내용의 불변 버전. |
| `template_clause_rules` | `template_revision_id`, `clause_id`, `condition_jsonb`, `sort_order`, `required` | 템플릿에서 조항 선택·순서 규칙. |
| `document_set_versions` | `id`, `product_id`, `version_no`, `product_revision_id`, `manifest_jsonb`, `status`, `created_at`, `change_reason`, `batch_id` | 발행 시점의 템플릿/조항 버전, 데이터, 파일 해시를 묶는 불변 manifest. |
| `document_files` | `id`, `document_set_version_id`, `document_type`, `format`, `page_no`, `storage_key`, `sha256` | 개별/통합 PDF 및 페이지별 PNG 파일. |
| `bulk_update_jobs` | `id`, `change_reason`, `target_snapshot_jsonb`, `status`, `created_at`, `completed_at` | 실행 당시 활성 상품 목록과 결과. |
| `audit_events` | `id`, `actor_id`, `action`, `entity_type`, `entity_id`, `before_hash`, `after_hash`, `created_at` | 변경·발행·실패 추적. 초기 버전은 최소 사용자 식별자와 시간 기록. |

**무결성 권장안:** `document_set_versions(product_id, version_no)` 유일 인덱스, 파일별 SHA-256 저장, 발행 상태의 스냅샷/파일 수정 금지, 종료 상품의 새 문서 발행 차단. 이력의 `manifest_jsonb`에는 각 문서의 템플릿 버전, 조항 버전과 순서, 제품 스냅샷 ID, 렌더러 버전, 출력 파일 목록을 기록한다. JSONB 색인은 실제 조회 패턴을 본 뒤 추가한다. 데이터 파일은 DB 행과 분리된 파일 저장소에 보관하되, DB의 저장 키와 해시로 검증한다.

## 7. 일괄 수정과 과거 상품 보호

**권장 절차:**

1. 공통 조항의 새 초안 버전을 만든다. 수정 사유를 필수로 입력한다.
2. 영향 분석 화면에서 참조 상품 중 `ACTIVE`만 추린다. 대상 수, 상품명, 현재 문서 버전, 변경 조항을 표시한다.
3. 미리보기로 변경 전후 문구와 대표 상품의 3종 문서를 비교한다.
4. 실행 시 대상 상품 ID와 상태를 다시 확인하고 `bulk_update_jobs.target_snapshot_jsonb`에 고정한다. 실행 중 상태가 `ENDED`로 바뀐 상품은 건너뛰고 결과에 남긴다.
5. 상품별로 새 `document_set_version`과 PDF/PNG를 생성한다. 실패 상품은 개별 실패로 기록하고 기존 발행본을 유지한다. 성공한 파일과 manifest가 모두 준비된 뒤에만 새 버전을 발행한다.
6. 결과 화면에서 성공·실패·건너뜀 수와 대상별 새 버전을 확인한다.

**금지 규칙:** `ENDED` 상품의 `product_revisions`, `document_set_versions`, `document_files`를 일괄 수정 작업으로 `UPDATE`하거나 삭제하지 않는다. 기존 발행 버전도 덮어쓰지 않는다. 저장소에서 해당 파일을 재생성해 같은 키에 덮어쓰는 방식도 금지한다. 배치 재시도에는 동일 작업 ID를 사용해 중복 버전이 생기지 않도록 한다.

## 8. API 초안 권장안

REST 경로는 구현 예시다. 서버는 모든 쓰기 요청에서 상태·스키마·버전 충돌을 검사한다.

| 메서드·경로 | 기능 |
|---|---|
| `POST /api/products` | 상품과 판매 구성 생성. JSONB 구성 검증. |
| `GET /api/products?status=ACTIVE` | 상태별 목록 검색. |
| `GET /api/products/{id}` | 상품 상세·판매 구성·현재 발행 버전. |
| `PATCH /api/products/{id}` | 초안 또는 활성 상품의 데이터 수정. 종료 상품은 거부. 낙관적 버전 검사. |
| `POST /api/products/{id}/preview` | 3종 및 통합본 미리보기. 발행 버전은 만들지 않음. |
| `POST /api/products/{id}/document-sets` | 검증 후 새 문서 세트 버전 발행. |
| `GET /api/products/{id}/document-sets` | 버전 목록. 생성 시각·사유·상태 포함. |
| `GET /api/document-sets/{versionId}` | 고정 manifest와 파일 목록 조회. |
| `GET /api/document-sets/{versionId}/files/{fileId}` | PDF 또는 PNG 다운로드. |
| `GET /api/templates`, `GET /api/clauses` | 템플릿과 조항 조회. |
| `POST /api/clauses/{id}/revisions` | 공통 조항의 새 버전 초안 생성. |
| `POST /api/bulk-updates/preview` | 변경 대상·제외 대상·문서 차이 확인. |
| `POST /api/bulk-updates` | 활성 상품 대상 배치 실행. 요청 ID로 중복 실행 방지. |
| `GET /api/bulk-updates/{jobId}` | 처리 결과와 오류 조회. |

**권장 응답 규칙:** 검증 오류는 필드 경로와 설명을 반환한다(예: `variants[1].composition.groups[0].items[2].label`). 종료 상품 수정은 `409 Conflict`, 변경 중 버전 충돌도 `409 Conflict`로 처리한다. 파일 생성이 오래 걸리면 발행 요청은 작업 ID를 반환하고 완료 후 버전을 노출한다.

## 9. 화면 구성 및 UX

1. **상품 목록:** 상태·법인·상품명 필터, 마지막 발행 버전과 수정일 표시. 종료 상품은 읽기 전용 표시.
2. **상품 등록/편집:** 기본 정보 → 금액대별 판매 구성 → 품목 그룹·항목 편집 → 문서 조합 확인의 단계로 구성한다. JSON 원문 편집은 고급 기능으로 두고 표 형태 입력을 기본으로 한다. 같은 상품명의 복수 금액대를 탭 또는 비교 표로 확인한다.
3. **문서 조합:** 공통 조항, 포함된 조건부 조항, 제외 사유, 순서를 보여준다. 상품명·법인 등 변수가 어디에 쓰였는지 확인할 수 있게 한다.
4. **미리보기/발행:** 약관, 주요 내용, 설명서, 통합본 탭을 제공한다. 누락 데이터·긴 표의 페이지 넘침·PNG 품질을 확인한 후 발행한다.
5. **공통 문구 수정:** 변경 전후 비교, 활성 상품 대상 목록, 종료 상품 제외 수, 실행 결과를 한 화면 흐름으로 제공한다. 실패 목록을 내려받거나 다시 시도할 수 있게 한다.
6. **문서 이력:** 버전 번호·발행 시각·사유·적용 조항 버전·파일을 표시한다. 이전 버전 PDF/PNG를 즉시 내려받을 수 있다.

## 10. 출력·버전 관리

**확정(기술 스택 채택):** Jinja2 HTML/CSS 템플릿을 Playwright for Python(Chromium)으로 PDF로 만들고, 생성된 PDF를 PDFium(`pypdfium2`)으로 페이지별 PNG로 변환한다. 통합본 PDF는 `pypdf`로 병합한다. 운영 렌더링은 `worker` 컨테이너에서 수행해 실행 환경(글꼴 포함)을 고정한다. worker는 Chromium과 탭을 띄워 두고 재사용한다. 두 포맷은 동일한 상품·템플릿·조항 스냅샷에서 생성해야 한다. 한글 글꼴을 포함하고 표의 줄바꿈·페이지 나눔·긴 문구·복수 판매 구성을 검증한다.

파일 명명 예시: `{상품코드}_v{버전}_약관.pdf`, `{상품코드}_v{버전}_상품설명서_p01.png`, `{상품코드}_v{버전}_통합.pdf`. 통합본 순서는 **약관 → 약관 주요 내용 → 상품설명서**다. 기존 버전의 파일은 보존한다. `PNG`는 페이지별 출력이므로 통합본도 페이지 순서가 명확한 파일 묶음으로 제공한다.

| 2. 조항·템플릿 | 공통/조건부 조항, 순서, 일반/결합 설명서, 주요 내용 | 조건별 미리보기 결과가 승인 샘플과 일치. |
| 3. 출력·이력 | 3종/통합 PDF, 페이지별 PNG, 문서 세트 버전·파일 보관 | 과거 버전 재조회와 파일 해시 일치. |
| 4. 일괄 수정 | 영향 분석, 활성 상품만 대상, 상품별 새 버전, 배치 결과 | 종료 상품 불변 및 배치 실패 격리 테스트 통과. |
| 5. 사용성 점검 | 실제 담당자와 상품 등록·공통 수정 수행, 화면 개선 | 담당자가 수작업 우회 없이 대표 시나리오 완료. |
| 후속 | 권한 모델, 외부 시스템 연동, 기존 문서 이관·원본 편집 방식 검토 | 별도 요구사항·연동 계약·이관 검증 계획 수립. |

## 13. AI 코딩 에이전트용 실행 프롬프트

아래 프롬프트는 저장소와 개발 환경을 확인한 뒤 단계별로 사용한다. 회의에서 확정되지 않은 조항 전문, 환급 수치, 법인 정보, 추가 비용 규칙은 예시로만 다루고 실제 발행 데이터에 임의 값을 넣지 않는다.

### 프롬프트 1: 프로젝트 분석 및 구현 계획

```text
첨부 개발 가이드의 확정된 업무 규칙, 기술 스택, 권장안을 분리해 읽어 주세요. 기술 스택은 가이드의 "기술 스택" 표(백엔드 Python 3.13·uv·FastAPI·SQLAlchemy·Alembic·Procrastinate·Jinja2·Playwright·pypdfium2, PostgreSQL, 프론트엔드 React+Vite)를 따르고, 저장소에 이미 코드가 있으면 충돌하는 부분을 알려 주세요. 먼저 backend/·frontend/·schemas/ 골격과 docker-compose.yml을 구성하세요. 약관·약관 주요 내용·상품설명서 3종, 복수 금액대, JSONB 품목, 불변 문서 버전, 활성 상품만 일괄 수정하는 기능을 단계별 작업으로 나누세요. 실제 조항 전문이나 법적 문구는 만들지 말고 필요한 승인 샘플을 입력 목록으로 남기세요. 파일 변경 전 구현 계획과 데이터 마이그레이션 위험을 제시하세요.
```

### 프롬프트 2: 데이터·API 구현

```text
개발 가이드의 DB/API 권장안을 가이드의 기술 스택(FastAPI, SQLAlchemy 2.x, Pydantic v2, jsonschema)으로 구현해 주세요. 개발 DB는 PC에 설치한 로컬 PostgreSQL이며(.env.example), 운영 배포는 docker-compose.yml로 구성하고, 스키마는 Alembic으로 관리하세요. 테스트는 pytest로 작성하세요. 상품 상태 DRAFT/ACTIVE/ENDED, 여러 판매 구성, 구성별 JSONB와 스키마 검증, 상품/템플릿/조항의 불변 버전, 문서 세트 manifest를 포함하세요. ENDED 상품의 편집·새 발행을 서버에서 차단하세요. 낙관적 버전 검사와 필드 경로가 포함된 검증 오류를 구현하고, 단일/복수 금액대 및 종료 상품 차단 테스트를 작성해 실행하세요.
```

### 프롬프트 3: 렌더링과 문서 이력

```text
승인된 샘플 문구를 입력받는 템플릿/조항 조합기를 구현해 주세요. 렌더링은 worker에서 Jinja2 → Playwright(Python) PDF → pypdfium2 PNG, 통합본은 pypdf 병합으로 처리하고 운영 이미지에 한글 글꼴을 포함하세요. 조건부 조항 포함 여부와 순서를 명시적으로 결정하고 약관, 약관 주요 내용, 일반형/결합형 상품설명서의 미리보기를 만드세요. 같은 스냅샷으로 개별·통합 PDF와 페이지별 PNG를 생성하고 파일 해시와 manifest를 저장하세요. 이전 버전 조회 시 현재 조항을 다시 읽어 출력 내용이 달라지지 않게 하세요. 한글, 긴 표, 페이지 나눔, 복수 판매 구성 결과를 검증하세요.
```

### 프롬프트 4: 일괄 수정 및 화면

```text
공통 조항 새 버전의 영향 분석 화면과 일괄 적용 작업을 구현해 주세요. 대상은 실행 시점 ACTIVE 상품만 포함하고 ENDED는 제외하세요. 실행 직전과 상품별 처리 직전에 상태를 재검사하세요. 기존 발행본을 덮어쓰지 말고 성공 상품별로 새 문서 세트 버전을 발행하세요. 실패는 상품별로 격리하고 재시도 시 중복 버전이 없게 하세요. 변경 전후 미리보기, 대상·제외·실패 목록, 문서 버전별 PDF/PNG 다운로드 화면을 제공하세요. A5~A8, A11 수용 테스트를 자동화해 결과를 보고하세요.
```

## 14. 착수 전 확인할 미결정 사항

1. 실제 약관·주요 내용·일반/결합 상품설명서의 승인된 원본과 조항 전문.
2. 법인별 변수, 대표자·시험 일자·선수금 등 공통 문구의 소유자와 승인 절차.
3. 판매 종료 판정 기준과 종료 시점, 재판매 상품의 상태 전환 정책.
4. 한 상품에 여러 금액대를 담을 때 문서별 표 배치와 최대 열 수.
5. 품목의 필수 입력값, 조건부 제공·추가 비용 문구, 이미지 자산의 관리 방식.
6. 출력 규격(용지 크기, 해상도, 파일명, 통합본 구성)과 기존 문서 이관 범위.

이 항목은 추측으로 확정하지 않는다. 실제 업무 샘플을 받은 뒤 템플릿과 검증 규칙에 반영한다.
