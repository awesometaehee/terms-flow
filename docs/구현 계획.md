# 구현 계획 (프롬프트 1 결과)

> 기준 문서: `약관·상품설명서 자동 생성 시스템 바이브코딩 개발 가이드.md`  
> 작성일: 2026-10-22

## 1. 저장소 현황과 충돌 검토

- 작업 시작 시 저장소에는 개발 가이드 문서만 있었다. 기존 코드·DB·데이터가 없으므로 가이드의 스택과 **충돌하는 코드는 없다.**
- **스택 변경 1건:** 가이드에 적은 MinIO 공식 Docker 이미지가 Docker Hub에서 내려가 받을 수 없다. 개발용 S3 호환 저장소를 **SeaweedFS(`chrislusf/seaweedfs`, Apache-2.0)**로 대체했다. 애플리케이션은 S3 API(`boto3`)만 사용하므로 운영 저장소 선택에는 영향이 없다.
- 로컬 PC에는 Python 3.13, uv, pnpm이 설치되어 있지 않다. 개발·실행·테스트는 모두 Docker 컨테이너 안에서 수행하는 것을 기본으로 한다.

## 4. 착수 전 받아야 할 승인 샘플 (입력 목록)

개발자가 임의로 만들지 않는다. 받기 전까지는 `[샘플]` 표시가 붙은 가짜 문구로만 개발·테스트한다.

1. 약관 원본(공통 조항 전문, 조항 번호 체계)
2. 판매 채널별 협력비 조항 문구와 적용 조건(온라인/오프라인 구분 기준)
3. 환급 방식별 문구와 비율 표기 방식
4. 결합 상품 조항과 결합형 상품설명서 블록
5. 약관 주요 내용 양식과 변수 목록(상품명, 법인 정보 등)
6. 일반형·결합형 상품설명서 양식, 단일/복수 금액대 실제 샘플
7. 법인별 공통 값(법인명, 대표자, 시험 일자, 선수금 문구)과 각 값의 승인 담당자
8. 품목 그룹·필수 품목, 추가 비용·제공 조건 문구, 이미지 자산
9. 출력 규격: 용지 크기, PNG 해상도(DPI), 파일명 규칙, 통합본 구성

## 5. 데이터 마이그레이션 위험

| 위험 | 영향 | 대응 |
|---|---|---|
| 기존 데이터 없음 → 초기 스키마는 자유롭게 바꿀 수 있지만, **첫 발행 이후** 불변 테이블(`*_revisions`, `document_set_versions`, `document_files`)은 구조 변경이 어렵다 | 과거 버전 재현 실패 | 불변 테이블은 컬럼 추가만 허용(삭제·의미 변경 금지). 스냅샷은 JSONB에 `schemaVersion`을 포함해 저장 |
| 품목 구성 JSON Schema 변경 | 기존 구성 검증 실패 | 스키마 파일을 버전별로 추가(`composition.v2...`)하고 저장 데이터의 `schemaVersion`으로 검증. 기존 버전 파일은 수정 금지 |
| 불변성을 애플리케이션 코드에만 의존 | 실수로 UPDATE/DELETE | 1·3단계에서 DB 트리거로 발행 행의 UPDATE/DELETE 차단 |
| Procrastinate 버전 업그레이드 | 작업 큐 스키마 불일치 | 초기 스키마는 Alembic 리비전에 고정. 업그레이드 시 Procrastinate 제공 마이그레이션 SQL을 새 Alembic 리비전으로 추가 |
| 렌더러(Chromium·Poppler·글꼴) 업데이트 | 같은 입력에서 다른 출력 | worker 이미지 태그를 고정하고 manifest에 렌더러 버전 기록. 과거 버전은 재렌더링하지 않고 저장된 파일 제공 |
| 개발용 저장소(SeaweedFS) → 운영 저장소 이전 | 파일 접근 경로 변경 | DB에는 버킷 상대 `storage_key`만 저장하고 엔드포인트는 환경 변수로 분리. 이관 시 SHA-256으로 검증 |
| Chromium이 Noto CJK(OTF/CFF) 글꼴을 PDF에 Type 3로 삽입 | 텍스트 추출은 되지만 일부 뷰어·인쇄에서 품질 저하 가능 | 3단계에서 TrueType 계열 한글 글꼴(예: Noto Sans KR TTF) 또는 회사 지정 글꼴로 비교 검증 후 확정 |
| 향후 기존 문서(PDF·인디자인) 이관 | 구조화 데이터 부재 | 이번 범위 밖. 이관 시 "외부 원본" 유형의 문서 세트로 별도 등록하는 방안 검토 |

## 8. 프롬프트 3(조합·렌더링·문서 이력) 결과 — 2026-10-22

### 흐름

1. `POST /api/products/{id}/preview` — 상품에 맞는 템플릿을 고르고 조항 포함·제외를 결정해 3종·통합본 HTML과 결정 사유를 돌려준다. 발행 버전은 만들지 않는다.
2. `POST /api/products/{id}/document-sets` — 같은 조합 결과로 PENDING 버전을 만들고, manifest에 템플릿·조항 리비전 ID와 순서, 제외 조항과 사유를 고정한 뒤 렌더링 작업을 큐에 넣는다 (202).
3. worker — manifest에 고정된 리비전만 읽어 Jinja2 HTML → Chromium PDF(문서별) → pypdf 통합본 → pdftoppm PNG(PDF별 페이지)를 만들고 저장소에 올린다. 모든 파일이 준비되면 한 트랜잭션에서 파일 행·SHA-256·renderer_version을 저장하고 PUBLISHED로 바꾼다. 실패하거나 그사이 상품이 ENDED가 되면 FAILED와 사유를 남긴다.
4. 조회 — `GET /api/document-sets/{id}`(manifest·파일), `GET /api/document-sets/{id}/html`(manifest로 다시 만든 HTML), `GET /api/document-sets/{id}/files/{fileId}`(PDF/PNG 다운로드, SHA-256 헤더 포함).

### 규칙 형식

| 항목 | 형식 |
|---|---|
| 레이아웃 | `schemas/layout.v1.schema.json`. 블록: `heading`, `paragraph`, `clauses`(제N조 번호 또는 번호 없음), `variant_table`(구성별 비교 표), `variant_prices`, `page_break` |
| 조건 (조항 포함·템플릿 선택) | `{"channel": ["OFFLINE"], "refund_type": ["A"], "bundle_type": ["BUNDLE"]}` — 키끼리 AND, 값 목록 안은 OR, 빈 객체는 항상 |
| 템플릿 선택 | 문서 종류마다 ACTIVE 템플릿 중 선택 조건이 맞는 것이 정확히 1개여야 한다 (0개·2개 이상이면 422 `COMPOSITION_ERROR`) |
| 선택 조항 | `required: false` 조항만 발행 요청의 `excluded_clause_keys`로 뺄 수 있다 |
| 변수 | 문구 안 `{{ product.name }}`, `{{ product.product_code }}`, `{{ company.name }}`, `{{ company.code }}`. 그 밖의 변수는 등록 시 422 |
| 파일 | `document-sets/{버전ID}/{상품코드}_v{버전}_{약관|약관주요내용|상품설명서|통합}.pdf`, `..._p01.png`. 키에 버전 ID가 있어 기존 파일을 덮어쓰지 않고, 같은 키가 있으면 업로드를 거부한다 |

### 검증

- 테스트 48개 통과 (worker 컨테이너). 렌더링 테스트 6개는 Chromium이 없는 api 컨테이너에서는 건너뛴다.
- A1·A12: 3종 개별 PDF·PNG와 통합 PDF·PNG 생성, 통합본 쪽수 = 개별 쪽수 합, 약관→주요 내용→설명서 순서, 다운로드 파일 SHA-256 일치.
- A2·A10: 구성 4개 × 품목 60개 설명서가 여러 쪽으로 나뉘고, 60개 행이 모두 순서대로 있으며 표 머리글이 쪽마다 반복된다.
- A3·A4: 오프라인만 협력비 조항 포함, 환급 방식·결합 상품 조건에 따라 해당 조항과 결합형 설명서 템플릿만 바뀐다. 번호는 포함 조항 기준으로 다시 매긴다.
- A7: 조항 개정 후에도 이전 버전의 manifest·HTML·저장 파일 해시가 그대로이고 새 버전에만 개정 문구가 들어간다.
- 실제 작업 큐 경로: 개발 DB에서 API → 큐 → worker로 발행해 PUBLISHED와 파일 10개를 확인했다 (상품 코드 `E2E…`, `[샘플]` 데이터).

### 남은 사항

- 한글 글꼴이 PDF에 Type 3로 들어가는 문제는 그대로다. 텍스트 추출은 정상이다. 회사 지정 글꼴 또는 TTF 글꼴로 교체할지 출력 규격과 함께 정한다.
- 실패(FAILED) 버전의 재시도는 4단계(일괄 수정·재시도)에서 다룬다.
- PNG 해상도 기본값 150dpi (`RENDER_PNG_DPI`), 용지 A4. 출력 규격 확정 후 조정한다.

## 9. 프롬프트 4(일괄 수정·화면) 결과 — 2026-10-22

### 일괄 수정 흐름

| 단계 | API | 내용 |
|---|---|---|
| 새 리비전 | `POST /api/clauses/{id}/revisions` | 공통 조항 새 버전과 수정 사유 |
| 영향 분석 | `POST /api/bulk-updates/preview` | 새 리비전이 들어갈 상품 중 **ACTIVE만 대상**. ENDED(판매 종료)·DRAFT(판매 전)·이미 반영됨·조합 오류는 사유와 함께 제외. 변경 전후 문구 |
| 실행 | `POST /api/bulk-updates` (202) | 영향 분석을 다시 수행해 대상·상태를 `target_snapshot_jsonb`에 고정. 상품마다 세이브포인트에서 상태를 재확인하고 새 문서 세트 버전(PENDING, `batch_id`)을 만든 뒤 렌더링 작업을 넣는다. 이전 발행본에서 사용자가 뺀 선택 조항은 그대로 뺀다 |
| 결과 | `GET /api/bulk-updates/{id}` | 상품별 결과: 진행 중·성공·실패·건너뜀과 사유. 렌더링 전에 종료된 상품은 발행하지 않고 건너뜀 |
| 재시도 | `POST /api/bulk-updates/{id}/retry` | 실패한 상품만 다시 처리. 렌더링 실패 버전은 같은 버전(같은 manifest)을 다시 렌더링하므로 버전 번호가 늘지 않는다 |

- 같은 `request_id`로 다시 실행 요청하면 새 작업을 만들지 않고 기존 작업을 돌려준다.
- 재시도해도 이전 파일을 덮어쓰지 않도록 저장 키에 렌더링 실행 ID를 넣었다: `document-sets/{버전ID}/{실행ID}/{파일명}`.
- 단일 버전 재시도: `POST /api/document-sets/{id}/retry`.
- 최신이 아닌 리비전으로 영향 분석·실행을 요청하면 409 `VERSION_CONFLICT`.

## 11. KMS 전환 — 2026-10-23

사용자 결정: 약관·상품설명서 구분을 없애고 **KMS**로 재구성. 기본 단위는 모듈+문서, 기능은 카테고리·태그·검색·PDF/PNG 출력, 상품 기능은 KMS 안의 한 메뉴로 유지, 공통 모듈 일괄 반영은 사용 중 문서에만. 승인 워크플로는 제외.

### 데이터 (Alembic 0005)

| 테이블 | 내용 |
|---|---|
| `categories` | 모듈·문서 공용 카테고리 트리 (`parent_id`) |
| `tags`, `clause_tags`, `document_tags` | 태그 |
| `variables` | 변수 정의: 키·이름·형식(글자/숫자/날짜)·기본값. `product.*`, `company.*`는 상품 문서 예약 키 |
| `clauses` (모듈) | `document_type`은 상품 문서용일 때만, `category_id` 추가 |
| `clause_revisions` | `content_json`(서식 본문) 추가. 기존 행은 일반 텍스트를 문단으로 변환해 사용 |
| `documents` | 제목·카테고리·상태·변수 값·검색용 텍스트·`lock_version` |
| `document_blocks` | 현재 단락 순서. MODULE(모듈 기준 리비전 + 문서 수정본) 또는 TEXT(직접 쓴 단락). 클라이언트가 만든 단락 ID 유지 |
| `document_revisions` | 저장할 때마다 단락 본문까지 담은 불변 스냅샷 |
| `publications`, `publication_files` | 문서 리비전의 PDF·PNG 발행본 |
| `bulk_update_items` | 대상이 상품 또는 문서 (`product_id` XOR `document_id`) |

보호 트리거: 문서 리비전 수정·삭제 금지, 발행된 발행본·파일 수정·삭제 금지, 종료 문서와 그 단락·리비전·발행본 변경 금지. 검색 색인: `pg_trgm` GIN (모듈 제목·본문, 문서 제목·검색 텍스트).

### 서식 본문

- 저장 형식은 화면 에디터(TipTap) JSON. 서버(`app/richtext.py`)가 허용 노드·서식만 받고, 출력 HTML은 서버가 직접 만든다(텍스트·속성 이스케이프, 링크는 http(s)/mailto만, 색상은 #hex/rgb만).
- 에디터가 붙이는 빈 속성은 저장·비교 전에 정규화한다. 화면도 같은 규칙으로 비교해 원본과 같으면 "수정됨"으로 보지 않는다.
- 상품 문서의 조항도 같은 서식 본문으로 출력한다 (변수는 강조 표시).

### API

`/api/categories`, `/api/tags`, `/api/variables`, `/api/search`, `/api/clauses`(모듈: 카테고리·태그·검색어 필터, `PATCH`로 정보 변경, `content_json` 리비전), `/api/documents`(목록·생성·복제·저장 `PUT`·상태·리비전·미리보기), `/api/documents/{id}/blocks/{blockId}/promote`(원본 모듈에 반영), `/api/documents/{id}/publications`, `/api/publications/{id}`(파일·다운로드·재시도), `/api/bulk-updates`(상품·문서 함께).

문서 목록(카테고리 트리·태그·상태·검색, 새 문서·복제), **문서 편집기**(끌어서 순서 변경, 단락 사이 +, 단락별 서식 편집기와 도구 막대, 변수 칩과 값 입력, 수정됨·새 버전 있음 표시, 원본으로 되돌리기·새 버전으로 바꾸기·원본 모듈에 반영, 미리보기, 발행·발행 이력·파일, 변경 이력), 모듈 목록·상세(서식 편집으로 새 버전 → 영향 분석), 변수 관리, 통합 검색, 일괄 반영(문서·상품 대상·제외 사유, 대표 문서, 결과·재시도·CSV). 상품 문서 메뉴는 그대로.

### 검증

- 백엔드 테스트 70개(Windows 로컬, 로컬 PostgreSQL 18): 서식 본문 검증·이스케이프·정규화, 카테고리·태그·모듈 필터, 문서 조합·순서 변경·문서 안 수정·원본 반영(충돌 포함)·복제·검색·종료 문서 보호(API·DB), 변수 누락 시 발행 거부, 발행 PDF·PNG, 문서 일괄 반영(사용 중·수정 없음만, 수정·작성 중·종료 제외), 기존 상품 문서 테스트 전부.

## 12. 현업 사용자용 UX 간소화 — 2026-10-23

모듈·변수를 저장하고 다시 고치는 과정이 어렵다는 의견에 따라 입력 단계와 용어를 줄였다. 데이터 구조와 API는 그대로이며, 화면에서 기본값을 채워 보낸다.

### 뺀 것
- 모듈 키·변수 키 입력: 내부 식별자(`m_…`, `v_…`)를 자동 생성하고 목록에서도 숨김
- 변수 값 형식 선택: 기본 TEXT
- 수정 사유 입력(모듈 저장, 원본 모듈 반영, 발행): 고정 문구로 기록
- 저장 후 영향 범위 화면으로의 강제 이동, 편집기 [x] 변수 버튼, 블록 배지의 버전 번호

### 바꾼 것
- 모듈 상세: 제목·카테고리·태그·본문을 한 화면에서 고치고 [저장] 한 번(Ctrl+S). 저장 후 같은 화면에 남고, 버튼이 "저장됨"으로 바뀜. 이전 버전은 접힌 목록에서 보기·되돌려 편집
- 저장 후 사용 중 문서가 있으면 안내 띠: [바로 반영] / 대상 자세히 보기 / [나중에]
- 변수: 행을 누르면 편집 창(저장·취소·삭제). 쓰는 곳이 있는 변수는 삭제 불가(`DELETE /api/variables/{id}`, 409 `VARIABLE_IN_USE`)
- 문서: "원본 모듈에도 저장"은 저장 안 한 변경을 먼저 자동 저장한 뒤 반영하고 같은 안내 띠를 보여 줌. 발행은 확인만. Ctrl+S 저장

### 검증
- 백엔드 ruff·mypy 통과, pytest 71개 통과(변수 삭제 테스트 추가)
- 프런트 타입 검사·단위 테스트 통과, 브라우저 시나리오(변수 편집·삭제, 키 없는 모듈 생성, Ctrl+S, 바로 반영, 자동 저장 후 원본 반영, 사유 없는 발행, 사용 중 변수 삭제 차단) 통과

## 13. 변수 값 일괄 반영 — 2026-10-23

변수 금액 등을 바꾸면 그 변수를 쓰는 사용 중 문서에 한 번에 반영한다. 모듈 일괄 반영과 같은 작업·결과 화면을 쓴다.

- 데이터 (Alembic 0006): `bulk_update_jobs`에 `variable_id`, `variable_value` 추가. 작업은 모듈 리비전 또는 변수 중 하나를 가리킨다(`ck_bulk_update_jobs_one_source`).
- API: `POST /api/variables/{id}/bulk-updates/preview`, `POST /api/variables/{id}/bulk-updates` (`request_id`, `overwrite_document_ids`). 작업 조회·재시도는 기존 `/api/bulk-updates/...`.
- 규칙
  - 기본값을 쓰는 사용 중 문서: 새 기본값으로 문서 리비전을 남기고 다시 발행한다.
  - 문서에 값을 따로 입력한 사용 중 문서: 사용자가 체크한 문서만 입력값을 지워 기본값을 쓰게 하고 발행한다. 나머지는 "입력한 값 유지"로 제외.
  - 작성 중(다음 저장 때 새 값 반영)·종료·이미 같은 값으로 저장된 문서는 제외.
- 모듈 일괄 반영: 반영 후 값이 비는 변수를 미리 알려 주고 그 자리에서 입력받는다(`missing_variables`, `variable_values`). 값 없이 실패한 문서는 본문 반영을 남기고, 결과 화면에서 값을 넣어 다시 시도한다.
- 화면: 변수 편집 창에서 저장하면 변수 목록 위에 반영 안내 띠(체크 목록 포함)가 뜬다. 결과 화면 제목은 "변수 [이름] → 새 값".

## 14. 모듈·변수·문서 삭제 — 2026-10-23

이력(문서 리비전·발행본·일괄 작업)이 참조하므로 행을 지우지 않고 `deleted_at`으로 숨긴다 (Alembic 0007·0008). 목록·검색·일괄 반영·새 본문에서 빠진다.

| 대상 | API | 삭제 조건 |
|---|---|---|
| 모듈 | `DELETE /api/clauses/{id}` | 작성 중·사용 중 문서와 상품 템플릿에서 쓰지 않을 것 (409 `CLAUSE_IN_USE`, 쓰는 문서 이름 안내). 삭제 후 상세는 읽기 전용 |
| 변수 | `DELETE /api/variables/{id}` | 삭제하지 않은 모듈의 최신 본문, 종료·삭제하지 않은 문서의 본문·입력값에서 쓰지 않을 것 (409 `VARIABLE_IN_USE`). 예전 모듈 버전·종료 문서는 막지 않는다 |
| 문서 | `DELETE /api/documents/{id}` | 작성 중·사용 중 문서만. 종료 문서는 보관 기록이라 삭제 불가 (409 `DOCUMENT_ENDED`) |
